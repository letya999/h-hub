# task-jobs: Job/Run machines with observed uncertainty

Status: accepted (owner decision, 2026-11-23).

## Context

A task can be lost mid-flight — the runtime container dies between
dispatch and report. Retrying blindly duplicates side effects; losing
it silently wedges the user.

## Decision

task-engine owns two `shared/fsm` machines. Job: `queued -> admitted ->
running -> succeeded|failed`, plus `cancelled`, `uncertain`,
`quarantined`; `failed` and `quarantined` are `LongLived` so only an
operator (`hubctl job retry|unquarantine`) re-queues them. Run:
`dispatched -> streaming -> settled` with a start-of-stream deadline;
`progress` reports re-arm via `fsm.Touch`. A lost run moves its job to
`uncertain` for a 15-minute observation window — never auto-retried;
the quarantine path is manual. Conversation order is FIFO on a durable
cursor; admission is capped per-owner (32) and global (64). A partial
unique index on `runs(owner, space, conversation)` where
`claim_released_at IS NULL` enforces one live run claim per session.
The claim is released in the same transaction as the run's final FSM
transition. `conversations.active_run` is unused and remains physically
until the next release's contract migration. Operator job calls use an
audited `ActAs` token: owner and space are checked against verified
claims before any read or write.

The current tuning values are 32 live jobs per owner and 64 globally
to bound queue pressure, 30 seconds to start a run stream and 45
seconds of streaming silence to detect a lost runtime. Uncertain jobs
are observed for 15 minutes without retry. These are adjustable policy
values, not proof thresholds; phase 3 carries the owner-ratified
defaults in code.

## Rejected

- Auto-retry on loss: the harness may have already acted; duplicates
  are worse than a visible `uncertain`.
- `failed`/`quarantined` as `Final`: machine validation rejects edges
  out of final states, and both have legitimate operator exits.
